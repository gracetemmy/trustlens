04 · Flare Integration

Four primitives. Remove any one and it breaks.

TrustLens needs an oracle, an external-data prover, a confidential runtime and an EVM to enforce the outcome. Flare is the only network shipping all four as first-class primitives, which is why this is a Flare product rather than a product that happens to deploy here.

Confidential ComputeFCC · TEE

Hosts the scoring extension as a Go service in a hardware-isolated enclave and signs results with a registered TEE identity. This is the only reason a lender can trust a score computed over data it cannot see. Contracts verify the signature with ecrecover against the machine registry.

Remove it → private evidence has nowhere safe to be processed. No product.
FTSOv2ORACLE

Live XRP/USD from ~100 independent providers, updating roughly every 1.8 seconds. Used deliberately twice, in two separate trust domains: as a model input inside the enclave, and again inside the contract as an independent collateral floor that the model cannot influence.

Remove it → collateral valuation depends on a centralised API the lender must trust.
Data ConnectorFDC

Attests XRP Ledger facts — account age, payment history, proven payments — so credit history becomes provable rather than self-reported. The enclave verifies proofs rather than believing claims.

Remove it → a borrower simply invents the evidence that earns a better rate.
FAssetsFXRP

Brings XRP — an asset with no native smart contracts — into a programmable lending position on an EVM chain. This is the collateral being underwritten, and the reason the use case exists on Flare specifically.

Remove it → XRP holders can't borrow against XRP without a custodial bridge.
Verified, not assumed

The integration details that actually bite.

These are the specifics we checked against a live Coston2 node rather than copying from a blog post — the small things that quietly corrupt collateral maths.

verified live against Coston2 · chain 114
// FtsoV2 on Coston2
const FTSOV2 = "0x3d893C53D9e8056135C26C8c638B76C8b60Df726";

// Feed ID = 0x01 (crypto category) + ASCII name, right-padded to 21 bytes
const XRP_USD = "0x015852502f55534400000000000000000000000000";

const [value, decimals, timestamp] = await ftsoV2.getFeedById(XRP_USD);

// Careful: decimals differ per feed. XRP=6, BTC=2, FLR=8.
// Assuming 18 is the classic way to corrupt collateral maths.
🔢

Per-feed decimals

Returned as a signed int8 that varies by feed and can change. Hardcoding 18 silently misprices collateral by orders of magnitude.

⏱️

Staleness checks

The feed returns a timestamp for a reason. A price that stopped updating during a crash is worse than no price, so the vault rejects stale reads.

✍️

Signer registry

The vault accepts an attestation only if the recovered signer is currently registered for the pinned extension ID. Rotation is handled on-chain.
